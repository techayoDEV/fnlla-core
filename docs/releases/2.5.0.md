# FNLLA Core 2.5.0

Core 2.5.0 introduces transport-independent application capabilities and fixes
nine findings from the runtime audit. PHP remains `^8.3`. There is no dependency
on FNLLA Full, an AI service or a provider SDK. Availability is established by
the matching immutable GitHub release, not this document or a local ZIP.

## Application capabilities

- Optional `ActionMetadata` extends existing action definitions with explicit
  input/output shapes, permissions, visibility, version and execution kind.
- `ActionExecutor` shares command transactions, receipts and outbox with legacy
  `ActionRunner`; query capabilities do not open mutation transactions.
- Trusted `ApplicationContext` providers and `ActionAccess` validate identity,
  tenant, permissions and resource access. Internal actions remain private;
  public outputs and schemas omit hidden fields.
- `ApplicationSchema` projects the existing registry for downstream adapters.
  Core adds no REST, MCP or SDK implementation.
- Enabled Product Modules can register actions through an optional interface.
  Legacy definitions, constructor signatures and persisted formats remain valid.

See [capabilities](../framework/CAPABILITIES.md) for registration and execution.

## Security and compatibility

Read the complete [hardening notes](../framework/AUDIT-HARDENING.md) before
upgrading. Intentional rejection changes are:

1. Disabled/revoked accounts cannot log in or retain authenticated sessions.
   Explicit `active` values must be true, integer 1 or string "1". A missing
   status field remains supported. Custom providers must return the requested ID.
2. Domain events restore a freshly authorized persisted actor/tenant context.
   Custom event containers must bind `TenantContextManager`. Revoked identities
   block domain delivery; historical audit delivery remains available.
3. Mail/queue effects and `afterCommit()` reject externally owned PDO
   transactions. Use managed transactions; invalidate and explicitly purge a
   connection after rollback failure. Nested failures cannot silently commit.
4. HTTP mail does not follow redirects and bounds responses to 1 MiB. Configure
   the final allowlisted endpoint; remove URL user information and fragments.
5. Unknown validation rules and malformed parameters fail as configuration
   errors. Required takes precedence over nullable; declared strings use length
   for min/max even when their content is numeric.
6. Module state replacement preserves the old file on failure and synchronizes
   readers with writers. Ensure the state directory permits its lock file.
7. Capability arrays cannot exceed 4096 items; impossible bounds fail during
   registration. Metadata exposes effective bounds; total payload budgets still
   apply independently.
8. Exception logs omit raw messages and trace arguments. Use correlation IDs,
   safe codes and structured fields for diagnostics; never log unlabelled secrets.

## Upgrade and rollback

1. Back up application data, queue/outbox state, module state and the dependency
   lock. Test custom providers, validators, event listeners and adapters.
2. Stop queue workers and outbox publishers. Install the immutable 2.5.0 artifact
   through Composer, verify its manifest/provenance and retain the previous lock.
3. No new database migration or queue format conversion is required from 2.4.0.
   Existing reliable-outbox configuration and side tables remain unchanged.
4. Review failed outbox deliveries for revoked identities and explicitly resolve
   them. Check runtime inspection, application requests, queues and diagnostics
   before restarting workers. Delivery remains at-least-once.
5. Rollback requires reverting application code using new capability contracts
   together with the Core dependency. Do not run old workers against applications
   requiring new identity rules. Returning to 2.4.0 also restores its audited
   vulnerabilities; use rollback only as a controlled recovery decision.

Capability receipt keys are separate from legacy keys. No automatic cleanup of
receipts, audit evidence or failed deliveries occurs during upgrade or rollback.

## Verification scope

Release gates include Windows/Linux package reproduction, PHP 8.3/8.4 quality,
MySQL/Redis, migration recovery, HTTP upload/mail boundaries, clean Composer
installation and the Full consumer/export suites. The published CI evidence must
identify this exact source commit. Local PHP 8.5 checks supplement that matrix.
Long-lived HTTP worker isolation and live AI-host/provider certification are not
part of this release. Existing external adapters remain application-owned.
