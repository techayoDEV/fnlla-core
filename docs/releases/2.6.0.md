# FNLLA Core 2.6.0

Core 2.6.0 adds opt-in resilience and FNLLA Navigation to the generated starter.
PHP remains ^8.3. Core remains MIT-licensed, provider-neutral and independent of
Framework, fnlla.com and AI services. Public availability requires the matching
immutable release and exact-commit CI evidence; a local ZIP is not publication.

## Resilience

- Typed dependency outages, isolated optional provider boot and safe production
  errors keep programming failures distinct from unavailable infrastructure.
- Explicitly approved stateless public GET/HEAD pages may use bounded last-known-
  good snapshots. Private sessions, accounts, purchases and package downloads
  are excluded. Failed or unsafe responses never replace a successful snapshot.
- Disposable cache failover, shared file-backed circuit breakers and bounded
  retries support optional dependencies. Retries require explicitly idempotent
  reads; writes and payments receive no automatic replay.
- Minimal live/ready health responses, request state and structured events expose
  degradation without leaking internal details. Public health routes remain off.
- Generated starters include a pre-bootstrap emergency guard and maintenance
  HTML, plus health, fallback:generate, down and up CLI commands.

Read [resilience operations](../resilience.md) before enabling features. All
advanced caching, public health and optional dependency policies default off.
Shared circuit state requires shared file storage; no distributed Redis circuit
adapter is supplied. Last-known-good refresh is synchronous. Emergency HTML is
not a substitute for independently configured proxy/static delivery.

## Navigation

The starter ships local, pinned Turbo assets with ordinary SSR links, compatible
shell persistence, scoped page/Region lifecycle and explicit read-only Region
navigation. Keyboard focus, route announcements and reduced motion are included.
Native POST, CSRF, redirects and full-reload opt-outs remain authoritative.
See [navigation contracts](../framework/NAVIGATION.md). Browser assets and their
MIT notice ship together; node_modules and build dependencies do not ship.

## Compatibility and upgrade

1. Back up application code, configuration and the Composer lock. Stop workers
   for dependency replacement, then install the exact immutable release through
   Composer and verify its provenance and manifest. Never patch vendor files.
2. No database migration, queue format change or automatic feature enablement is
   introduced by upgrading from 2.5.0. Existing capability/action contracts remain.
3. Existing applications retain their own entrypoints. Adopt the new emergency
   guard and optional middleware deliberately; inspect generated starter examples.
4. Custom callers that caught PDOException on connection creation should handle
   DependencyUnavailable instead. The original exception is retained as previous.
   Production APP_DEBUG cannot expose exception details.
5. Test normal requests, dependency outages, authorization, payment callbacks,
   downloads and recovery in your deployment. Configure cache paths and bounded
   retention explicitly. Never approve personalized or nonce-bearing HTML.
6. Restart workers after successful checks. Rollback restores the previous lock
   and application adapters together. Disable new features before returning to
   2.5.0, which does not implement these resilience contracts.

## Release evidence

The release must pass PHP 8.3/8.4 on Windows/Linux, MySQL/Redis service and upgrade
checks, Apache upload checks, deterministic package builds and fresh Composer
verification. Compare both CI ZIP hashes with the locally verified archive.
Consumer checks cover Framework/site adapters, private-request exclusions,
Stripe behavior and starter exports. Operator-specific proxy/FPM failure drills
remain deployment acceptance, not a claim of guaranteed availability.
