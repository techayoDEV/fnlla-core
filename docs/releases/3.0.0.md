# FNLLA Core 3.0.0

Core 3.0.0 is the stable edition of FNLLA's provider-neutral MIT Web Framework
foundation, requiring PHP `^8.3`. The owner authorized this exact release and
the subsequent Framework 5.1.0 release on 2026-10-20, conditional on all required
final-source gates. This document records scope and migration; it is not a CI,
publication or production-deployment receipt. Verify the matching official
`v3.0.0` tag, release assets and `CI-EVIDENCE.json` before consumption.

The [official v3.0.0 release](https://github.com/techayoDEV/fnlla-core/releases/tag/v3.0.0)
was published on 20 October 2026 after final-source acceptance. Its accepted
source is `fc9270a6d3af6196dc514dea7b73db134455024c`. This maintained guide may
receive clarifications; the original tag and assets remain unchanged.

The preceding immutable stable release is Core 2.8.1. The rc.1/rc.2 review notes
and artifacts remain historical evidence for their exact sources. They do not
substitute for final stable acceptance and are not overwritten by this release.

## Core 3 boundary

The breaking change removes implicit product-specific configuration refresh.
Applications explicitly select live top-level fields with
`app.live_config_fields`. Selected values have application-only authority in
fresh and cached modes: removing a selected application field removes it from
the effective configuration, even if an old package default still exists.
Null/invalid declarations and malformed caches fail closed without using an
old credential as fallback. Ordinary non-selected defaults retain their normal
merge semantics.

Trusted integrators may declare `FNLLA_REQUIRED_LIVE_CONFIG_FIELDS` before Core
bootstrap. Its validated selection is unioned with the application declaration
within the same combined limits of 32 namespaces and 32 fields per namespace.
An application cannot disable required fields with an empty selection. The
selection defines freshness, not account permissions. FNLLA's compatible
Framework bootstrap supplies its own required Workspace selection; Core itself
does not depend on Workspace, the commercial Framework, TechAyo or an AI account.

A historical `developer_access` namespace without a valid `users` selection
fails before it can supply cached credentials. The namespace is recognized only
for the migration diagnostic; it does not register old routes, classes or account
APIs. Immutable Core 2.8 packages retain their original behavior.

`config:cache` compiles through the actual configuration loader with old cache
reads disabled. Validation precedes atomic publication, preserving the previous
cache on failure. Linked configuration files are rejected. With active OPcache,
configuration source bytecode is invalidated before evaluation, including when
timestamp validation is disabled. Restricted or unavailable invalidation fails
closed. Real bytecode tests cover cached/fresh rotation, removal and restricted
APIs; this is not a promise that deployments can skip an OPcache/process restart.

Standard bootstrap captures the configuration generation before environment and
configuration loading. Standard queue/outbox workers refuse the next reservation
after watched inputs change, and stale cache compilers cannot publish. A
config-free minimal bootstrap remains valid; adding its configuration directory
changes the generation. This fence cannot stop an active handler, observe an
external secret authority or manage arbitrary application writers. Drain writers,
restart workers and reconcile current revocations during update and rollback.

Core 3 also hardens invalid CSRF token handling and private rejection redirects,
updates generated application test discovery and limits the lightweight analysis
fallback to application-owned sources. Existing applications own their generated
tooling and migrate it through review; installing the library does not silently
overwrite their files.

Published queue interfaces, Actions, authorization/tenant contracts, receipts,
outbox and snapshot formats remain supported. Core introduces no mandatory AI
provider, account, destructive database reset or automatic integration activation.
See the [runtime contracts](../framework/RUNTIME-CONTRACTS.md),
[security boundaries](../framework/SECURITY-PRIMITIVES.md) and
[readiness scopes](../framework/READINESS.md).

## Installation

Use the matching [getting-started guide](../framework/GETTING-STARTED.md).
For an existing Composer application select the official public VCS repository
and exact stable version:

```console
composer config repositories.fnlla-core vcs https://github.com/techayoDEV/fnlla-core.git
composer require techayodev/fnlla-core:3.0.0
composer check-platform-reqs
```

Review and commit the resulting lock and verify the installed source reference
against the official `v3.0.0` tag. Composer's default registry is not the authority
for this package's identity. Do not substitute a similarly named package or
disable source/artifact verification. The official release ZIP is a separately
verified distribution carrying manifest and provenance files; a Git source ZIP
does not have the same identity.

New applications may use `php fnlla make:project` from the official tagged source
or selected library. The generated project bundles Core as a local immutable
path package and retains application-owned routes, configuration and data.

## Upgrade from Core 2.x

1. Identify the original installed package, source and lock, custom adapters,
   package defaults and application credential fields. Read every intervening
   [upgrade boundary](../framework/UPGRADING.md). A Framework application must
   consume the Core accepted by its Framework release; do not bypass that lock.
2. Rehearse on an isolated copy. Add `live_config_fields` to the existing
   returned array in `config/app.php`, preserving its other entries. A historical
   namespace selects `'developer_access' => ['users']`; custom credentials
   select their actual fields. A trusted compatible integration can supply its
   documented required bootstrap map. Keep selected values in application-owned
   configuration, never only in package defaults. Missing means revoked.
3. While still on the old Core, rebuild `php fnlla config:cache`, or remove only
   the generated `storage/framework/cache/bootstrap-config.php` with writers
   stopped. Rebuild declaration changes before switching dependencies. An old
   cache without a required declaration deliberately fails under Core 3.
   Never clear queues, sessions, application cache, logs or business data as
   migration housekeeping.
4. Drain HTTP writers, workers, schedules and external writers. Retain matching
   code, exact Composer files, configuration, database, uploads, private files,
   encryption keys and external queue/session state, and verify restore. Install
   the reviewed exact Core target through Composer in a separate release
   directory; do not edit `vendor/` or bundled package implementation.
5. Rebuild configuration with Core 3, restart workers/OPcache through the normal
   deployment mechanism and verify critical application behavior. Assert cached
   and fresh permission equivalence, login/denial, credential rotation/removal,
   service readiness, custom adapters, pending jobs and outbox delivery.
6. Rehearse both a completed upgrade and failure after dependency installation
   but before activation. Restore the old code and exact lock, use compatible
   data/snapshots when formats change, rebuild generated cache and repeat the
   application checks before restoring traffic. A code rollback preserves
   current identity revocations; never reactivate credentials or role assignments
   from a stale `.env` or data backup. Keep old data-decryption keys separate.

This configuration change requires no database migration or destructive reset.
Application schema changes require their own reviewed migration and recovery.
Restoring a ZIP cannot undo external effects or reconcile already-delivered
outbox state. A failed recovery check leaves writers stopped. If startup reports
a missing declaration, restore the previous dependency set and complete the
configuration preparation; do not disable the guard or reuse stale credentials.

## Final acceptance and distribution

Release Verified requires the final clean remote-main source, all **15 Core
checks** on PHP 8.3/8.4/8.5 with native Linux/Windows coverage, deterministic
Windows/Linux release ZIP equality, retained manifest/provenance verification
and clean Composer consumption. The required jobs include MySQL/Redis,
checksum-pinned original 2.3.1/2.8.1 upgrade/crash/recovery/rollback drills,
HTTP upload/mail boundaries, package/starter checks and the documented developer
exercise. Core's full Framework consumer/export/migration acceptance is also
required. Report omitted platform boundaries explicitly. The owner-approved
signed local venue retains the same 15 checks and uses a dedicated GitHub App,
versioned source policy, external trusted controller key/policy, latest signed
sequence, original log/artifact verification and source-specific protected
checks. Hosted Actions remains a separate venue; unsigned local reports or PR
checks alone do not establish final-main acceptance. The release gate's
`CI-EVIDENCE.json` names the actual venue. See the
[signed local procedure](https://github.com/techayoDEV/fnlla-core/blob/v3.0.0/docs/RELEASING.md#signed-local-native-venue).

After verified Core publication, Framework 5.1.0 must pin the official immutable
3.0.0 release through Composer and its verified installer, then pass its own
complete final-source/final-lock release matrix and artifact checks. The owner's
authorization covers this sequence, but Core's 15 checks and earlier Framework
results using Core 2.8.1 or an RC cannot replace that separate technical stage.
The accepted Framework 5.0.0 package retains its original Core 2.8.1 dependency.

Stable publication changes no application deployment, customer catalogue,
entitlement, license, repository visibility or optional provider activation.
Engineering Verified and Release Verified do not establish Deployment Verified
for a particular host, integrations, capacity, monitoring, backup policy or
RPO/RTO. The [developer exercise](../framework/DEVELOPER-EXPERIENCE.md) supports
reproducibility; independent new-developer usability acceptance remains separate
before broad promotion. No comparative productivity or superiority claim is made.
