# FNLLA Core 2.8.0

This is the next stable release target, prepared from the 2.7.2 baseline.
Availability requires the matching immutable release, exact-commit CI and owner
authorization. A local review package proves only the behavior actually tested.

## Scope and compatibility

Core 2.8.0 adds provider-neutral package configuration and view resolution, plus
an optional package-publication file transaction. Existing constructor calls,
CLI names, Actions, authorization, queue formats and database contracts remain
compatible. The additional public APIs justify a minor release. Core remains
usable without Full, a Developer Panel or any AI/search provider.

`FNLLA_CONFIG_DEFAULTS_ROOT` may be defined by trusted bootstrap before
`load_config_directory()` to point at a package's PHP configuration directory.
Environment loading must precede configuration evaluation. Application maps
override defaults recursively; lists, empty arrays and explicit null replace
their corresponding values. There is no automatic package discovery or change
to ordinary Core starter configuration.

`View::path(string $template): string` returns an existing PHP template path.
The application `VIEW_ROOT` wins over the optional ordered `view.paths` list
(at most 16 trusted roots). Invalid roots, traversal and symlinks that escape a
root are rejected. Missing directories are skipped; a missing template fails.
Neither configuration roots nor template roots may come from HTTP input.

`FrameworkUpdateTransaction` accepts the optional second constructor argument
`package-publication`. Its payload is limited to `config/`, `routes/`, `views/`,
`public/assets/`, `public/vendor/fnlla-runtime/` and
`.fnlla/package-publication.json`. It does not authorize writes: the calling
application must check permissions, approved content and conflict policy first.
The callback must mutate only the journaled paths; this class is a recovery
primitive, not a filesystem sandbox. Package distribution continues to reject
the default legacy framework update mode.

Before a transaction changes files, it stores `recovery.php` and its SHA256
receipt beside the journal. A trusted recovery entrypoint must validate the
receipt and reject linked paths before requiring this component. The journal's
operation must match the recovery transaction. Older journals without an
operation remain valid in default `framework` mode. Unknown or mismatched
operations fail before restoring any file and retain the journal/backups.

## Upgrade and first run

1. Back up application files and the database; test restoration in isolation.
2. Install the reviewed immutable Core 2.8.0 package through the application's
   configured Composer source and retain the exact lock. Do not patch `vendor/`
   or an offline package cache to simulate an upgrade.
3. Clear disposable bootstrap configuration caches after changing package
   defaults, configuration roots or overrides; rebuild them with the intended
   environment. Developer credential values are refreshed from effective source
   configuration even when cached. Removed credential configuration clears the
   cached users value.
4. Run application tests, `runtime:inspect` and `runtime:doctor`; exercise the actual
   adapters, workers and routes used by the application. `/api/health` proves
   liveness only. Full must be validated against this exact package separately.

Fresh Core applications retain their existing local `.env` setup, application
configuration and ordinary CLI. No Developer Panel account or setup is added.
PHP `^8.3` and required extensions remain unchanged; MySQL and Redis extensions
are needed only for their selected adapters. No database/queue migration is
required from 2.7.2, and no new external calls are enabled by default.

## Operations and rollback limits

File transactions preserve only their declared file payloads. They do not roll
back database migrations, uploads or customer data. Keep transaction metadata
outside the public document root and writable only by trusted application and
maintenance identities. A checksum detects accidental/tampered bytes relative
to its receipt; it is not a signature and does not protect against an attacker
who controls both the component and receipt. Application-wide backup/recovery
remains a separate capability and operational responsibility.

Rollback may restore the previous immutable dependency and application files
after draining workers. Restore a database snapshot when domain changes require
it, and revalidate before reopening traffic. Configuration/view fallback roots
must then refer to the rolled-back package; stale caches must be cleared again.

## Maintenance baseline

Once the exact release is approved and published, 2.8 is the frozen Core feature
baseline for FNLLA 4.1 applications. Subsequent work is limited to reviewed bug,
security and compatibility fixes with regression tests, patch release notes and
the same release gates. Review maintenance weekly; urgent security fixes may
require an earlier patch. This policy is not a claim of unlimited support or a
service-level agreement. Deferred product/provider features remain upstream.
