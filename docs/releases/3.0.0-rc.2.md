# FNLLA Core 3.0.0-rc.2

Status: local review candidate, `release_approved=false`. The published stable
release remains 2.8.1. This document describes the proposed Core 3 contract and
does not authorize publication, dependency activation or production deployment.

## Proposed Core 3 boundary

This candidate supersedes the privately reviewed rc.1 after owner comments.
The owner has not approved stable publication. Earlier rc.1 artifact/matrix
results remain evidence for that source, not final rc.2 acceptance.

Selected fields have application-only authority in fresh and cached modes;
null declarations/malformed caches fail closed. Standard bootstrap records a
configuration generation; queue/outbox workers reject a changed generation
before reserving another item and stale compilers cannot publish bootstrap cache.
Active handlers still require operational drain/restart. See the named assertions
in `tests/ConfigurationSecurityTest.php`, [readiness scopes](../framework/READINESS.md)
and [the developer exercise](../framework/DEVELOPER-EXPERIENCE.md).

Core remains a provider-neutral MIT Web Framework foundation with PHP `^8.3`.
It does not require Workspace, an AI provider or the commercial Framework.
Published queue interfaces, Actions, authorization/tenant contracts, receipts,
outbox and snapshot formats remain supported. Existing original upgrade and
rollback fixtures remain immutable.

The breaking change is the removal of implicit product-specific configuration
refresh. Applications explicitly select live top-level fields with
`app.live_config_fields`; selected values are reloaded from application-owned
configuration files even when bootstrap configuration is cached. Package defaults
cannot restore a selected credential.
Missing values are removed, preserving the application's denial default.

A legacy `developer_access` namespace without an explicit `users` declaration
fails before it can supply cached credentials. The namespace is recognized only
to diagnose an incomplete migration; Core does not provide accounts or old
Workspace routes/classes. Existing Core 2.8 packages keep their original behavior.

`config:cache` now compiles through the same loader as bootstrap with cache reads
disabled. Unselected package defaults are retained, application maps/lists/null retain
their merge semantics, and invalid live declarations fail before cache replacement.

## Upgrade from Core 2.x

1. Identify the installed immutable package/lock, custom adapters, configuration
   defaults and application-owned credential namespaces. Review the intervening
   [upgrade boundaries](../framework/UPGRADING.md). Framework applications must
   wait for a Framework release that explicitly accepts the new Core package.
2. In an isolated copy, add `live_config_fields` to the existing returned array
   in `config/app.php`. Preserve existing entries; for the historical namespace
   include `'developer_access' => ['users']`. For other credentials declare their
   actual namespace/fields. Do not copy example account data into configuration.
3. While still running the old Core, rebuild with `php fnlla config:cache`, or
   remove only the generated `storage/framework/cache/bootstrap-config.php`
   while writers are stopped. An old compiled cache without
   the declaration is deliberately rejected by Core 3. Never clear queues,
   sessions, application caches, logs or business data as migration housekeeping.
4. Stop writers and workers, retain matching code/data/configuration/key backups,
   then install the reviewed target through Composer. Do not edit `vendor/` or
   the bundled package. Rebuild configuration with the new Core and restart
   workers/OPcache through the normal deployment procedure.
5. Verify login/denial, credential rotation and revocation with caching enabled,
   configuration overrides, application tests, queues/outbox, service readiness
   and recovery. Rehearse rollback to the original lock and compatible snapshot.

No database migration or destructive reset is introduced by this configuration
change. An application requiring other schema changes must review those separately.
If startup reports a missing declaration, restore the old dependency set and
perform steps 2-3; do not disable the guard or reuse a stale credential cache.

## Framework compatibility and release acceptance

The candidate declares Framework 5 as its intended consumer generation. A
Framework version's own Composer lock remains authoritative; 5.0.0 still pins
Core 2.8.1. Candidate integration must use a separate immutable local-review
artifact and isolated consumer, preserving canonical locks and offline caches.

Core 3 stable requires complete exact-source native Linux/Windows checks,
on PHP 8.3, 8.4 and 8.5,
deterministic artifact/clean Composer consumption, MySQL/Redis and original
2.3.1/2.8.1 upgrade/crash/recovery/rollback drills, HTTP upload/mail security,
Framework consumer/export/migration acceptance and a separate owner decision.
Keep failures, skipped boundaries and unsupported environments explicit.
Local synthetic checks do not establish customer hosting, capacity, RPO/RTO,
provider activation, external delivery or a security certification.
